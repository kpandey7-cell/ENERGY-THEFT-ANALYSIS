# Database Schema (InfluxDB)

## Overview
The platform utilizes **InfluxDB OSS 2.x** as its time-series database (do not migrate to InfluxDB 3.x). This provides highly optimized storage and querying capabilities for high-frequency IoT data and anomaly analysis using Flux.

### Top-Level Structure
- **Organization**: `energy_analytics_org`
- **Bucket**: `smart_meter_data` (Stores both raw telemetry and anomaly records)

## Measurements

### 1. `electricity_consumption`
Stores high-frequency telemetry data generated by the virtual smart meters.

**Tags (Indexed strings for fast querying/grouping):**
- `meter_id`: UUID of the virtual meter.
- `meter_type`: E.g., `residential`, `commercial`, `industrial`.
- `zone`: Geographical or logical grouping (e.g., `north`, `south`, `substation-a`).

**Fields (Actual recorded metrics):**
- `power_kw` (float): Instantaneous real power.
- `energy_kwh` (float): Cumulative or interval energy consumption.
- `voltage` (float): Supply voltage (e.g., 120V, 230V).
- `current` (float): Current draw in amperes.
- `power_factor` (float): Efficiency metric (0.0 to 1.0).

**Timestamp:**
- Time of the reading, tracked down to the nanosecond/millisecond.

### 2. `anomaly_events`
Stores anomalous patterns identified by the Anomaly Detection engine. By storing this as a time-series measurement in the same bucket, Grafana can easily overlay anomalies on top of raw consumption graphs.

**Tags:**
- `meter_id`: UUID of the meter that flagged the anomaly.
- `meter_type`: Inherited meter type for aggregated filtering.
- `zone`: Inherited zone for geographical filtering.
- `method`: The algorithm used (e.g., `z-score`, `rolling_mean`, `isolation_forest`).

**Fields:**
- `score` (float): The calculated anomaly magnitude/score.
- `details` (string): JSON stringified metadata containing extra context or parameters about the anomaly event.

**Timestamp:**
- Time the anomaly occurred (aligns with the corresponding `electricity_consumption` timestamp).
